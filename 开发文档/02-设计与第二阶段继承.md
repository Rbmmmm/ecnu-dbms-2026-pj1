# 设计与第二阶段继承

## 先确定业务语义

以下是 P0 的问题清单；最新确认状态以 `08-设置与需求确认.md` 为准。B-001—B-016主要业务规则已确认；下面保留问题背景，具体结果以确认文件为准，不重新将已确认项当作待决建议。

| 问题 | 建议讨论方向 | 影响 |
|---|---|---|
| 必须登录与匿名填写 | 可考虑登录后提交，但对问卷创建者隐藏身份；明确服务端是否保留关联、哪些接口可见 | 权限、重复填写限制、匿名承诺 |
| 多选跳转 | 明确包含任一、包含全部或完全匹配的条件含义；明确多个规则命中的优先级 | 规则结构与可重复验证的路径 |
| 数字跳转 | 确定支持的比较运算、边界包含关系及未命中规则时的默认下一题 | 条件表示与边界测试 |
| 循环与无效跳转 | 确定是否只允许向后跳转、能否直接结束、如何拒绝不存在的目标 | 发布校验与终止性 |
| 跳过的必答题 | 区分未访问的题与已访问但漏答的题；明确回退修改答案后失效答案如何处理 | 服务端重算路径、答卷保存和统计 |
| 多次填写 | 区分合法重复填写、双击重复请求、网络重试；明确次数限制 | 提交标识、约束、并发与统计口径 |
| 问卷发布后修改 | 优先讨论冻结题目结构的简单方案；若允许修改，需要问卷版本或题目快照 | 已有答卷能否按原题解释 |
| 截止、关闭与提交 | 明确在进入时还是提交时检查，以及临界时刻的规则 | 时间测试、状态流转 |
| 人数与次数 | 明确允许重复填写时，选项计数按答卷还是去重用户；明确空值、未访问题与零值 | 统计正确性与匿名设计 |
| “每次填写都保存” | 明确是否指每次完成提交，还是还要求中途自动保存；不得自行宣称必须有草稿功能 | 数据状态与工作范围 |

## 设计说明怎么体现思考

围绕具体业务比较方案，而不是列一串技术名称。重要决定使用短记录：背景与约束、候选方案、选择理由、代价、验证办法、未来何时重审。方案被改变时保留旧决定的适用版本与替代原因。

优先分析的问题包括：题目嵌入问卷还是独立集合；答卷如何独立保存；跳转规则如何表达；匿名与重复提交如何兼容；发布后如何保护历史题意；统计从哪些数据计算。

此前以用户、问卷、答卷三个业务集合作为起点，现已定案为三个业务集合加sessions辅助集合。题目与规则嵌入问卷，答卷独立增长。字段、索引与代价见[11](11-数据与架构设计.md)，本页保留分析方法，具体实现以11—13为基线。所有业务数据按要求放在 MongoDB；测试日志、源码和文档不是业务数据。

课程中已有的嵌套、引用、索引方法优先采用。需要额外机制时说明它解决的具体问题，不为扩展性引入插件平台、通用规则语言或微服务。

## 第一阶段应留下的扩展基础

| 基础 | 第一阶段需要明确的约束 | 第二阶段的用途 |
|---|---|---|
| 稳定标识 | 问卷、题目、选项使用稳定标识，引用不能只依赖数组位置或题号 | 调整排序或补充内容后能解释旧引用 |
| 数据结构版本 | 评估简单 schema 版本标识；区分数据库结构版本与问卷内容版本 | 判断老文档如何读取或迁移 |
| 题意保留 | 在发布冻结、内容版本或快照中选择满足当前需求的最简方案 | 旧答卷不因题目改变而失去含义 |
| 规则数据化 | 校验限制、条件和目标存为数据，后端统一解释 | 新条件只修改对应规则处理，不改整套流程 |
| 职责清楚 | 分开认证权限、问卷管理、规则判定、提交、统计；不必拆成多个服务 | 将变更限制在相关模块 |
| 明确接口 | 记录输入输出、错误与权限，不让网页自行决定业务是否合法 | 新界面或新功能复用原有逻辑 |
| 兼容样本 | 固定第一阶段问卷、答卷和期望统计 | 第二阶段检验旧数据和旧功能 |
| 版本基线 | 保留提交代码、依赖、schema、运行说明和测试结果 | 证明在原系统上演进 |

稳定标识不能单独保证历史兼容；还必须保留旧题目语义。schema 版本字段也不等于已经具备迁移能力，真正的迁移须在实际变更发生时实现和验证。

## 第二阶段继承验收

1. 记录第一阶段基线版本，不另建替代系统丢弃原实现。
2. 将每条新需求对应到受影响的集合、字段、API、规则、页面和测试。
3. 对结构变化明确采用兼容读取还是迁移；若需迁移，先备份，在隔离副本试运行，明确重复执行与失败恢复办法。
4. 用第一阶段固定样本检查旧问卷可访问、旧答卷可解释、旧统计符合原定口径。
5. 运行原有回归测试。需求明确改变的行为可调整期望，但必须记录原因，不能通过删除失败测试掩盖回归。
6. 同时验证新功能，报告修改前后结构、必要性、代码调整及兼容性问题。

未知的新需求不能提前保证全部兼容。当前要保证的是修改路径清楚、原设计有记录、旧数据有证据可核对。
