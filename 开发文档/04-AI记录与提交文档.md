# AI记录与提交文档

本文件按日期保留真实工作包历史；各记录中的“本轮”“下一步”“未实现”仅指所属轮次，当前状态见[交接](agent-handoff.md)。文档同步不能把旧轮结果改写为最新结果。

## 目标与边界

用工作包记录展示如何约束 AI、选择方案、发现错误、验证结果和推进系统演化。用户无需人工逐条抄录对话。日志由 AI 随工作整理，提交时压缩为有证据的过程记录。

助教明确要求真实记录工具、提示词、得到的代码、是否修改及修改内容，并总结 AI 的帮助、错误、自己的修改和设计。说明未要求提交所有聊天，因此采用“可核查的工作包日志 + 代表性案例 + 总结”。如果教师后续规定统一格式或完整日志，再补充适配。

文风自然来自具体问题、取舍和证据，而不是伪造人工编写过程。AI 提出的方案、编写的代码和完成的修复如实归属；用户提出的要求、选择、检查和修改也如实记载。用户确认方案不能写成用户独立设计或亲手编码。

## 两层记录

### 开发用记录

按完整任务单元建立工作包，例如需求分析、数据模型设计、跳转实现、提交一致性、统计核对、发布验收。功能的小修复直接追加到所属工作包；影响设计或暴露关键错误的修复单列案例。

每个工作包记录：

| 字段 | 内容 |
|---|---|
| 编号与日期 | W-xxx，实际开始与完成时间，状态 |
| 目标与约束 | 关联需求和验收标准，提供给 AI 的教材、代码或已有设计 |
| 工具 | 实际使用的 AI 工具；模型名称仅在可确认时记录，不猜测 |
| 提示词 | 实际用户指令的必要原文摘录，标明“原文摘录”；内部组织的任务描述另标“任务摘要” |
| 产出 | 得到哪些设计或代码，关联文件、函数或提交版本；规划工作没有代码就写无代码产出 |
| 审查与取舍 | 哪些建议采用或拒绝，依据是什么，决定由谁提出和确认 |
| 修改 | 修改前后行为、原因、执行者；无修改则如实写无 |
| 验证 | 关联测试编号、预期、实际、证据及未解决限制 |
| 人的参与 | 仅记录用户实际提出的问题、约束、决定和亲自执行的检查 |

不要把事后整理出的理想提示词冒充当时输入。对真实提示词可做脱敏和无关上下文删节，但须标注；缺少原文时只能记摘要及缺失情况。能够保留的关键指令在本工作包结束时及时摘录，不依赖日后还能恢复整段聊天。

### 提交用记录

按工作包整理精简日志，保留“工具—提示词摘录—产出—修改—验证”的闭环。通常选择 3—5 个实际发生、最能说明思考的案例展开，其余工作包用简表覆盖。不是必须凑够案例数，数量随实际过程决定。

可以重点选择：数据嵌套与独立集合的取舍；可配置跳转的规则语义；匿名与重复限制的冲突处理；用固定答卷发现统计错误；第二阶段旧数据兼容。它们只是候选主题，不预先宣称 AI 在这些地方犯过错误。

普通概念答疑、重复读取文件、格式调整和工具重试可省略或合并；如果答疑改变了需求理解或架构决定，则保留其结论、理由和来源。

## 如何体现使用 AI 的能力与规范

| 能力 | 报告里应当出现的实际证据 |
|---|---|
| 给出有效约束 | 用题目边界、课内方法、现有代码和验收样本限定任务 |
| 评价候选方案 | 记录为什么选一个方案、另一个方案在哪个业务上代价更高 |
| 检查生成结果 | 通过接口、数据库状态和独立预期发现问题，而非仅接受“已完成” |
| 迭代改进 | 根据明确失败输入修改设计或代码，再运行回归 |
| 管理上下文 | 每个工作包使用最新需求、已确认决策和第一阶段基线 |
| 如实说明贡献 | 区分 AI 产出、用户判断和实际操作，承认尚未确认的假设 |

不要求用户为了日志故意制造提问或手工修复。重要节点只集中讨论需要人的判断的事项，其余记录由 AI 自动维护。

## 本轮补充的执行方式

工作包开始时关联 R 编号和评分维度，结束时按 [每轮检查](06-要求对照与每轮检查.md) 记录结果。真实提示词摘录之外，记录传入的需求版本、已确认决策和完成条件，让读者理解 AI 如何受到约束。编程与审查是两个步骤；没有实际使用独立审查模型时，不写成多模型独立验证。

工作包可包含多轮修改，只保留影响结果的变化；不要求用户逐轮确认日常实现。关键设计选择由用户参与，最终文档由用户审核。写作按 [编辑规范](07-提交文档编辑规范.md) 执行。

## 提交文档结构

后续使用独立的 `提交文档/` 目录，建议包含：

1. `项目完成报告.md`：目标与范围、系统设计概览、关键取舍、实现与验证结论、实际问题与解决、AI 使用总结、局限。以此为总入口，引用详细文档。
2. `系统与数据库设计.md`：角色和流程、集合示例、字段与索引、嵌套及引用的理由、跳转与校验、历史数据保护。记录已经采用的设计，而非堆叠候选方案。
3. `运行与API说明.md`：依赖、配置、启动、示例流程、接口输入输出、权限与错误。不得包含真实凭据。
4. `测试用例与结果.md`：测试环境与版本、数据前提、步骤、输入、预期、实际、结果，以及代表性缺陷回归。
5. `AI使用日志.md`：完整工作包索引、精简过程记录、真实提示词摘录与重要案例。报告中只总结，不重复整份日志。

是否合并为一个最终报告或导出 PDF，在提交格式明确后决定。不得因为以往 Notebook 实验需要 PDF，就推断本项目必须使用相同的完整 Notebook 导出流程。

## 文档如何随开发形成

P0 形成需求解释；P1 形成设计初稿和决策记录；P2/P3 每完成一个工作包同步实际 schema、接口、规则和测试；P4 把实际验收数据补齐；P5 根据这些记录编辑成提交文档；P6 检查文档对应的代码版本。

开发记录保留历史原因，提交文档描述当前系统。对理解演进有价值的旧方案，在报告中简短说明为什么被替换；无关试错不全部倾倒进去。

写作以具体事实为单位，例如“多条规则同时命中时按保存顺序选第一条，发布时检查目标存在”，而不是“设计了灵活高效的规则引擎”。此处用于示范具体表达；实际规则已在08和12确认，采用情况与测试结果以所属工作包证据为准。

每个关键设计段落尽量回答：遇到什么问题，考虑过什么，最后为何这样做，代价是什么，用什么验证。无需每段套同样的小标题，也不人为添加口语、错误、虚构时间线来制造人工痕迹。
